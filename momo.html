momoDesign systems / Foundations for AI-assisted work

From scattered tokens.
To rules AI can follow.

Connecting values, semantic roles, and component usage to lay the groundwork for AI-assisted design and development.

FOCUS

Design systems &
structured reference design

YEAR

2026

OUTPUT

Web reference prototype

CONTRIBUTION

Token architecture, component mapping
& reference experience

AI-assisted interface work needs more than a list of colours and sizes. It needs clear guidance on which rule to use, where it applies, and how it relates to a component’s state. The existing Figma variables and front-end appendix contained useful definitions, but these relationships were not consistently structured.

I rebuilt the reference around reusable roles and explicit component mappings, then made them inspectable in HTML. This creates a clearer basis for people and code-capable AI assistants to interpret the same rules. The delivered prototype establishes that structure; a dedicated AI data interface and generation evaluation are next steps.

CHALLENGE

Useful definitions existed, but their relationships across values, component use, and states still required interpretation.

STRATEGY

I connected reusable roles, component references, visual examples, and implementation mappings in one structured HTML reference.

RESULTS

The rebuilt system makes rules more explicit, reuse more visible, and component choices easier to trace—giving people and source-reading AI assistants a clearer basis to work from.

01 / BEFORE & AFTER

Useful definitions.
Missing connections.

The front-end document provided an important foundation: seven token categories, primitive and semantic definitions, implementation mappings, and usage recommendations. My rebuild extended that work into a reference that explains how the rules relate to components and states.

For AI-assisted work, the important improvement is the clarity of the relationships. HTML provides an inspectable interface and structured source data; the component mappings explain which rule to choose. Open items also make some unresolved definitions visible.

❌Before

The original reference left people and AI assistants to interpret key relationships.

  • Interpret inconsistent naming to distinguish content roles, spacing contexts, and radius usage.
  • Infer component choices when tokens were not explicitly mapped to a component’s state or direction.
  • Assemble text styles manually from separate font size, line height, and weight definitions.
  • Reconstruct information from PDF tables to connect values, purposes, and implementation references.
  • Find unresolved decisions in scattered notes, with a risk of treating provisional rules as complete.

✅What I have done

I rebuilt the reference around reusable rules and explicit usage context.

  • Standardised naming by role and context, using body, heading, inset, container, shape, and image groups with descriptions and mappings.
  • Created 57 component-reference records across typography, spacing, radius, and shadow to make intended choices traceable.
  • Defined 14 reusable type roles and 24 usage mappings, separating shared text specifications from component states.
  • Structured 309 token definitions in HTML source, with explicit data fields, visual previews, and implementation context for human review and source-reading AI.
  • Surfaced open items and contextual token gaps, including the missing Chip disabled-background semantic token, so unresolved rules can be identified for review.
02 / NAMING

A clear structure.
Shared rules with context.

I organised naming around three questions: how a name expresses purpose, which layer it belongs to, and how the same token can serve different components.

01 / NAMING STRUCTURE

Group by purpose.
Identify the scale.

Semantic names combine a role or context with a numbered tier. The name identifies the family; its description and mapping explain the value and intended use.

Three layers answer three different questions

I separated raw values, reusable meaning, and actual component use. Typography, spacing, radius, and shadow include a component-reference layer, while colour, motion, and z-index currently expose primitive and semantic layers.

  1. PRIMITIVE

    What is the underlying value?

    Colour ramps, font sizes, a 4px spacing grid, radius values, and shadow definitions establish the available scale.

  2. SEMANTIC

    What purpose does it serve?

    Text roles, inset and container spacing, shape and image radius, and elevation names give values a reusable meaning.

  3. COMPONENT REFERENCE

    Where is the token used?

    Reference tables connect components and states to their typography, horizontal and vertical padding, radius, and elevation choices.

03 / COMPONENT

Document the choice.
Reduce the guesswork.

I created 57 component-reference records across typography, spacing, radius, and shadow. They connect reusable rules to specific components, states, and directions.

Define the style once.
Reuse it across components.

I combined font size, line height, and weight into 14 reusable text roles, supported by 24 usage mappings. Components share a style while their states remain documented separately.

Make the rules inspectable.
For people and AI.

I organised 309 token definitions in HTML source records with fields such as token, base, and value. Component records add state or direction where relevant. A code-capable AI assistant can inspect these relationships without reconstructing PDF tables.
